## Fix list for asof-platform
- [council-e2e] backend/pipeline/api.py (watch) + backend/platform/watchers.py — beat 5 fails: watch stays held_for_approval with watch_id null even after approve (CLI and MCP); watchers.test() is a stub returning {ok:true} and nothing calls it or on_alert from CLI/MCP, so no line ever goes STALE — wire watch->activate after approval, expose a watch test/poll step that calls on_alert(stale_line_ids) and re-attests so the affected line shows STALE (CLI + MCP).
- [council-e2e] backend/platform/mcp_server.py — no issue/cost tool, so beat 4 (approve, kill mid-send, restart) is CLI-only. Fine if the demo uses CLI; the demo script must say so. Beat 4 itself is covered by tests/platform test_chaos_kill_restart (passes).
- [council-robustness] backend/platform/util.py:39 (append_jsonl) — A torn tail (no trailing newline) is never healed, so the next append glues onto it and the good line is lost. effects.jsonl: has_effect() returns False for a key that was just recorded, so the action re-runs (double send). watch_alerts.jsonl: the same loss breaks dedupe. Repro: write '{"key":"a1","act' to effects.jsonl, append_jsonl({"key":"k9"}), and has_effect("k9") is False; the file reads '{"key":"a1","act{"key": "k9"}'. Fix: before appending, check that the file ends in "\n" and write a leading "\n" if not (or truncate to the last newline). read_jsonl should also try to recover glued objects.
- [council-robustness] backend/crust/ledger.py:58 (Ledger.add) and :45 (Ledger.__init__) — The ledger has the same torn-tail problem, and it also undercounts. Append is plain open("a") with no fsync and no newline healing, and the load loop stops at the first bad line. Repro: write 2 entries, append a torn fragment, add a third. The reload gives total 4.0 and 2 entries (true 6.0), so the credit is lost. A garbage line in the middle gives 1 entry and total 2.0 (true 4.0). The cap is checked against this total, so a corrupt ledger lets the run overspend. Fix: skip bad lines and keep reading; heal the tail before appending; fsync; and use O_APPEND with a single os.write, as util.append_jsonl does.
- [council-robustness] backend/crust/ledger.py:23 (PRICES) with client.py:96 (_credits) — /company/identify is not in PRICES, so a live or record identify call is ledgered at 0 credits unless the response carries a credits header. session.py RECORDED_UNIT_CREDITS says 0.2 per identify, so the cap and cost line undercount. Repro: with a mocked 200 identify, ledger.total stays 0.0 (an enrich-only 2.0 was observed). Fix: add "/company/identify" with 0.2 per match (or per request) to PRICES, taken from config.
- [council-robustness] backend/platform/actions.py:134 (sandbox_send) — The module docstring says "sandbox_send, which dedupes on key", but the code does not. A kill after the append to sandbox_outbox.jsonl and before the effects.jsonl append (the known window) means the re-run appends the payload again. Fix: in the outbox path, skip the append if a line with the same idempotency_key or key already exists (a cheap read_jsonl check). For the webhook path, send the key in an Idempotency-Key header as well as the body.
- [council-robustness] backend/platform/runstate.py:75 — float(state.get("elapsed")) raises ValueError, uncaught, on a state file that is valid JSON but has a non-numeric "elapsed" (e.g. {"steps":{"a":1},"elapsed":"x"}). load_state only validates "steps". Valid-JSON-but-wrong-shape is treated as torn for lists (OK), but not here. Fix: validate or coerce elapsed in load_state, and treat failure as torn.
- [council-robustness] backend/crust/client.py:165 and cache.py:52 — Malformed 2xx enrich bodies ({"weird":1}, [], null, or company_data as a string) are accepted as ok=True and cached to disk. They can also be billed: a bad match with a string company_data was ledgered at 2.0. A poisoned cache entry then replays the same SOURCE_UNAVAILABLE on every later run. The pipeline still refuses correctly (see PASSED), so this is hardening only. Fix: validate the shape per endpoint before cache.put and before ledger.add.
- [council-robustness] tests/platform/demo_actions.py:1 — It runs directly with `python tests/platform/demo_actions.py` only with PYTHONPATH=<repo root> (otherwise ModuleNotFoundError: backend, and the harness then reports "got 0 effects"). The demo payload also uses "key", while the real issue path uses "idempotency_key". Fix: add a sys.path insert, and document the exact chaos command in council/README.md.
- [council-safety] backend/platform/mcp_server.py:128-133 — The MCP server exposes `approve(key)` as an agent-callable tool, and it takes any raw idempotency key. The same agent that drafts an irreversible action can approve and issue it, so approval is not a separate human step. A key can be approved before the artifact exists. — Make approval a human-only channel (CLI or UI, not an MCP tool). Or require a human token or confirmation, and have `approve` take an artifact id and check that it is a held artifact.
- [council-safety] backend/platform/actions.py:80 (`execute`) — The public `execute` runs fn without checking approval. - [council-safety] backend/platform/actions.py:134-145 — `sandbox_send` POSTs to any URL in $SANDBOX_WEBHOOK_URL with no host or scheme check. A mis-set env var would send case files to an outside party. — Allow only http(s) on localhost or an allow-listed sandbox host from config, and refuse otherwise (fall back to the outbox).
