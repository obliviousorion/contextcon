## Top-3 concerns
1. **The core "trade"/pricing output has no ground truth.** `list_markets`/`trade` return an LMSR "aggregated estimate" price — labelled honestly as not-a-fact, but it is still the product's live-run deliverable most of the time (markets sit open before `close_date`). A hidden test can specify a correct *settlement*, but cannot specify a correct *fill price* — there's no sourced right answer for "what should the price be." If screeners probe anything other than a past-dated settlement, the demo has nothing checkable to show, same failure mode the council already flagged in Receivables Sentinel.
2. **Stateful trading breaks the "exactly once" story that AsOf earned for free.** AsOf's actions are idempotent because each is keyed by (entity, field, as_of) and order-independent. LaneBook's `trade()` mutates a shared LMSR price path — order-dependent. The doc says trades go through the same outbox/idempotency-key pattern, but doesn't address what happens if the process is killed mid-trade with other trades already queued: replaying "exactly once" per intent doesn't guarantee the *price path* is reproducible if concurrent trades from multiple desks were in flight. This is a genuine new robustness hole AsOf didn't have, and the doc hand-waves it as "same pattern as AsOf's dedupe key" without showing the ordering fix.
3. **"Refused at creation" criteria validator is the right instinct but under-specified for hidden-test lookalikes.** §6 says a criterion like "market sentiment turns negative" is rejected, and §7 shows one default-question refusal — good. But there's no stated rule for borderline criteria (e.g., "headcount data exists but is >14 days stale at close" vs "no record type at all") — the EXTENDED/CANNOT VERIFY/refused-at-creation three-way split needs a crisper, written decision table or a hidden test with an ambiguous criterion will land on the wrong bucket.

## Fatal flaws
None outright fatal — `settle()`'s refusal-first design is as deterministic and testable as AsOf's `attest()`, and the dedupe/outbox pattern for one-shot effects is sound. But concern #1 means a meaningful fraction of the live-run surface (anything shown before settlement) is a labelled-but-still-ungradable proxy, which caps the score below 5.

## Recommended merges/changes
- Cut the multi-desk LMSR pricing layer for the stage demo entirely (the doc's own cut-list already suggests this) and lead every test case with `settle()` outcomes only — don't let a judge see a "price" at all until the kill-restart/exactly-once demo is already won on deterministic ground.
- Write an explicit three-way decision table (REFUSE-AT-CREATE / EXTENDED / CANNOT VERIFY) with the exact conditions for each, and add one hidden-test case per branch — right now only CANNOT VERIFY and one REFUSE example are shown.
- Add a concrete answer, not just "same pattern as AsOf," for what happens to in-flight trades when the process is killed between two trades that both touch the same market's LMSR state — show the serialization/locking rule, not just the idempotency key.
